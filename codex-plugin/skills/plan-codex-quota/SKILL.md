---
name: plan-codex-quota
description: Use Resetwise to plan when to use saved Codex reset cards, prefill a Resetwise link, or find another equally good plan in a follow-up.
---

Run `scripts/resetwise.mjs` with Node, resolving the path relative to this skill. All command inputs except `read` are JSON on stdin. By default the helper sends the planning inputs to `https://codex-resetwise.vercel.app`. For local development, point `RESETWISE_BASE_URL` at a running local Resetwise server.

1. Read the current account's usage with `read`. If the host already offers a read-only Codex usage tool, use it and pass its structured result to `normalize` instead. Use only the main Codex bucket. Treat a returned 300-minute window as active. For current personal Pro tiers, a missing 300-minute window means weekly-only. On other plans, ask when this is unclear. Use actual card expiry timestamps and ask about missing card details only when needed. Never redeem or buy a reset as part of planning.
2. Before calculating a new plan, reuse the paid-access end time and renewal intent already given in the conversation. Ask for missing details together. If renewal intent is unclear, ask whether to stop at expiry, renew the same tier, or switch tiers. For prepaid terms, use the paid term's expiry. Resolve dates in the user's local timezone and state any assumption about an unknown time.
   - To stop at expiry, pass `subscription.renew: false`. To renew the same tier, pass `subscription.renew: true`. For continuous renewal only, also pass `subscription.allowLapse: false`.
   - To model a switch, pass `settings.tierChange` with `to`, `at` in epoch minutes, and `weeklyPercent`. Tier keys are `plus`, `pro100`, `pro200`, and `pro500`. The helper infers `from` from the usage snapshot and includes the next term. Ask for the current tier if it cannot be identified, then pass it as `from`. For a switch scheduled at renewal, use the end of paid access as the effective time and state that assumption if the exact time is unknown. Ask for a missing target, time, or weekly quota ratio together with any other missing details.
   - `weeklyPercent` is the target tier's full weekly quota as a percentage of the starting tier's. For example, use `10` if the user assumes the target gets one tenth of the current tier's weekly quota. Use a ratio the user provided or agreed to model and label it as an estimate. For a switch to Plus, `shortAmount` is the five-hour allowance as a percentage of the target weekly quota and defaults to 16%.
   - The next term defaults to monthly. For annual renewal, set `subscription.renewDays` to the actual duration of the next term, 365 or 366 days.
   - Pass `{ "usage": <normalized snapshot>, "settings": { "subscription": { "end": <epoch minutes>, "renew": <boolean> } } }` to `first` and ask about any other `missing` fields. Use 0 grace days and ask about the purchase channel only for channel-specific cancellation instructions. Preserve requested healthy hours. Other optional settings include `subscription.channel`, `subscription.billingDay`, `mode`, `hours` as two minutes-of-day values, `card.restart`, `resets` and `cards` as arrays of epoch minutes, `weekly` as `{remaining,end}`, and `short` as `null` or `{remaining,end,amount}`. The default five-hour cap is 16%.
3. If `first` or `more` recommends a `restart` renewal, confirm the user can let paid access lapse and is willing to rejoin the same plan, unless they already confirmed it. If they decline or cannot confirm, rerun `first` with the same usage and settings plus `subscription.allowLapse: false`. Reply with the total, baseline without cards, and `steps` in order. For each card, report its time range, the quota immediately restored at the example time when `restored` is present, and the net gain over the full plan (`gain`). Report weekly and five-hour restoration separately because both can constrain the same usage. Include the renewal time and kind when the plan renews. For a `tier-change` step, report the source, target, effective time, and weekly ratio used. Label totals and gains using `quotaBasis` so that a full week of the starting tier equals 100%. After a real switch, use a fresh usage snapshot for the next calculation. Link to `url` so the user can calculate and adjust on the website. Keep `context`, usage, and settings for later requests.
4. When the user asks for another plan with the same inputs, pass `{ "context": <latest context> }` to `more`. Add `action` using a card number or `"renewal"` and `direction` using `-1` for earlier or `1` for later when requested. Present the returned plan in the same format. `recalculated` means the previous plan included a grace period and this is the new first plan. An `exhausted` result means that search has no unshown equal-quota alternative. For a temporary failure, keep the existing context for a retry.
